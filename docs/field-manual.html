Forge Field Manual

How to run the apprenticeship · companion to the §1–§10 spec

Forge is the mentor. This is the machinery around it: what to run, in what order, and which parts of it are not yours to negotiate with. It assumes nothing about which model you are running, or whether you have ever written a line of code.

Two ways in

Forge is not tied to Claude, and it does not require you to already know how to program. Those two facts give you a choice, and for most people arriving here the first column is the right one.

no install

You've never programmed

Open any chat model you already have. Paste one file into it. Say "start". That is the entire setup — no terminal, no Node, nothing to install.

→ Route A, below

full capability

You're comfortable in a terminal

Clone the repo, run two commands, and the mentor can read your files, run your tests, and see the real error. This is the reference setup, and the only one that can assess debugging.

→ Route B, below

What each route can actually do

The prompt works out which of three runtimes it is in before it speaks, and records it. This is the part worth reading before you choose, because it is what the choice costs.

RuntimeWhat it isWhat you lose
agentic+hooksClaude Code with the guard hook installedNothing. This is the reference.
agenticAny agent with a shell and file access: another CLI, an IDE agent, a local model behind an agent harnessThe enforced write path. Replaced by the file-mode guard in Route B.
chatA plain chat window with no toolsFile access, the CLI, git history, and any honest read on level 5.

What you actually give up, stated plainly

  • Chat cannot assess level 5. "Debugs" means diagnosing a failure the model watched happen. A model that cannot run anything is taking your word for it, and levels only move on observed evidence. The prompt is told to be slower to promote past 4 and to say why — expect that, and don't argue it into a 5.
  • Chat has no validation and no history. No schema check, no atomic write, no git. The ledger is regenerated from scratch each session, and regenerated documents drift — long lists quietly get shorter. Check wins and misconceptions haven't shrunk.
  • Chat suspends two rules. "Never carry your own state" and "never print the ledger in chat" both stop applying, because neither is possible to honour without a CLI. That is the only place the spec gets overridden.
  • No dashboard flips §7.1. "Don't recite what they can see" only holds while you can see it. Without the board the mentor has to tell you where you are, out loud, every session.
  • Context length is the real limit, not the brand. Prompt plus ledger is roughly 25k tokens before the session starts, and it grows all year. A small local model will accept all of it and then silently drop the lesson cycle and the gates — which are the entire product. Before trusting one with a year, check it will still refuse to advance a phase you haven't earned.

Route A — start in a chat window

Three steps. None of them require anything installed.

  1. Get the prompt

    Open FORGE-PROMPT.md from the repo — the whole file, roughly 95 KB of text. You do not need to understand it. You need to copy it.

  2. Paste it into your model as the system prompt

    Anywhere with a long context window works. If there is no "system prompt" box, paste it as your first message instead and then send a second message saying start.

  3. Save what it gives you

    At the end of every session it will print a block of JSON. Save it in a file called ledger.json — anywhere, your desktop is fine. Next session, paste that file in first. That file is your entire progress; without it, session two starts over from nothing.

    Keep the previous two versions beside it as ledger-1.json and ledger-2.json. In this mode there is no undo, and those two files are it.

What you're trading away, and when to stop trading it

  • The mentor cannot run your code, so it cannot watch you debug — and debugging is the top rung of the ladder. It is instructed to be slower to promote you past level 4 and to say why. That is correct behaviour, not the model being difficult.
  • There is no validation and no history on your ledger. It is regenerated from scratch each session, and regenerated documents drift — check that your wins list never gets shorter.
  • This is temporary and it is meant to be. Phase 0 teaches you the terminal, Node, npm and git — which is exactly what the full setup needs. At the end of Phase 0 you will be able to do the setup below yourself, and doing it counts as Phase 0 work rather than a chore. The mentor is told to offer it then and not before.

→ Your setup is done. Continue at Running a session.

Route B — part one: the machinery

The same on every tool. It assumes you can already use a terminal — if you cannot yet, take the chat route above and come back at the end of Phase 0.

  1. Install and build

    cd ~/projects/the-forge
npm install
npm run setup

    This builds the ledger CLI, writes FORGE-PROMPT.md at the repo root — the prompt itself, which every tool needs — and puts forge-ledger in ~/.local/bin. It also writes a Claude Code skill, which you can ignore if you are not using Claude Code.

  2. Confirm the CLI is reachable

    which forge-ledger
# /home/you/.local/bin/forge-ledger

    Nothing printed means ~/.local/bin is not on your PATH. Add it to your shell profile — without it, the mentor cannot read or write your ledger at all.

  3. Protect the ledger

    A hand-edited ledger fails silently, so something has to make a direct write impossible. Which thing depends on your tool.

    Claude Code can refuse a write before it happens. Add this to ~/.claude/settings.json, merged with whatever is already there:

    "hooks": {
  "PreToolUse": [{
    "matcher": "Edit|Write|MultiEdit|NotebookEdit",
    "hooks": [{
      "type": "command",
      "command": "<repo>/scripts/guard-ledger.sh"
    }]
  }]
}

    Everything else gets the same protection from the filesystem:

    npm run protect-ledger    # chmod 444 ledger.json

    A stray edit then fails with EACCES while forge-ledger writes normally, because it replaces the file by renaming a new one over it. Run it once you have a ledger — it has nothing to protect before session one.

  4. Verify

    forge-ledger show

    Your ledger, in §7 order. If it says no ledger exists, your first session runs onboarding.

Route B — part two: teaching your tool the prompt

Every tool has some way to give a model standing instructions it will follow across a whole conversation. Whatever yours calls it, that is where FORGE-PROMPT.md goes — whole, never summarised.

MechanismTools that work this wayWhat you do
A named skill or commandClaude Code skillsWrite it to the skill file; invoke it by name
An instructions file the tool loads by itselfCodex CLI and others via AGENTS.md; Gemini CLI via GEMINI.md; Cursor and Continue via their rules filesPut the prompt in that file, or point the file at it
A system-prompt box or saved personaChatGPT projects and custom instructions; Gemini Gems; Ollama and LM Studio system prompts; any API playgroundPaste the prompt in

Tool conventions move faster than this page does. If a filename here has changed, the shape is what matters: find the thing your tool reads before every message, and put the prompt there.

On Claude Code — the whole skill, by hand

A skill is one Markdown file in a named folder. Nothing more:

mkdir -p ~/.claude/skills/forge
# then write ~/.claude/skills/forge/SKILL.md as:
#   the frontmatter below, a blank line, then all of FORGE-PROMPT.md
---
name: forge
description: Run a session of the Forge apprenticeship. Reads the
  learner's ledger, opens as the spec directs, teaches, and writes
  back what was demonstrated. Invoke when the learner types /forge.
---

The folder name is the command, so skills/forge/ gives you /forge. The description is what Claude reads to decide the skill applies, which is why it names the trigger explicitly.

npm run install-skill does exactly this and nothing else — it concatenates the frontmatter and the prompt into that path. Do it by hand once if you want to see there is no magic in it. Restart Claude Code afterwards, or the skill list will not include it.

On anything else

  • Find your tool's standing-instruction mechanism from the table above.
  • Give it all of FORGE-PROMPT.md. It is around 95 KB — long, but the gates and the lesson cycle are the product, and a summarised version quietly drops both.
  • If the tool loads a file by path, point at the file so it stays in sync when you rebuild. If it wants text, paste it and re-paste after any change.

Check it took. Open a session and ask: "which runtime are you in, and how do you know?" A model that has actually loaded the prompt names one of agentic+hooks, agentic or chat and says it tested by running forge-ledger show. Anything vaguer means the prompt did not land, and you are talking to a helpful assistant rather than to Forge.

Running a session, start to finish

The same seven moves every time, whichever hours you keep.

  1. Open the board first

    cd ~/projects/the-forge && npm run dev
# http://localhost:5173

    Read the Pick up here card before you read anything else. It was written for exactly this moment — by someone who knew you would arrive with no memory of last time. Do what it says.

  2. Open Claude Code in the project you are building

    cd ~/path/to/your-project
# then open your agent here — claude, codex, gemini, cursor…

    Not in the-forge. On an agentic runtime Forge can read your files and run your tests, and that is most of its value — start it where the work is.

  3. Start the session

    On Claude Code that is /forge. On any other tool it is whatever invokes the standing instructions you set up in part two — often just opening a conversation in the project or persona that holds the prompt, then saying start.

    That is the entire prompt. Do not summarise last session, do not paste your ledger, do not explain where you left off. Forge reads the ledger itself before it says a word, and it knows more about your last ten sessions than you do. (The one exception is the chat runtime, which has no way to read a file — there, pasting the ledger is the first move, and Forge will ask.)

  4. Start the timer when you actually start

    Not when you sit down — when the first block begins. Everything the dashboard says about your week depends on this being honest.

  5. Work the cycle

    A session opens with a one-line orientation and a warmup retrieval check on something you haven't touched in a few sessions. Then the block itself. Expect to be asked to predict output before running it, to break something that works, and to explain it back without the metaphor. Those three are where the learning lands; they are also the ones that feel skippable.

    If you are flat, say so. There is a menu — push, consolidate, play, cold check, lab — and choosing consolidate three sessions running is pacing, not slipping.

  6. Say when you can come back

    Forge asks at the close: which days, and roughly what hours. Answer with the truth rather than the plan you wish you kept — "Tuesday and Thursday mornings, Saturday if the week is kind" is a better answer than "most evenings" if most evenings is aspirational.

    It uses this for pacing, not pressure. Nobody is checking whether you showed up, and the number never becomes a deadline (§1: the constraint is not the goal). What it does is stop the plan being sized for a week you do not actually have — the commonest way these programmes fail is a schedule built on hours that were never real.

    If your availability changes, say so at any open. That is a planning conversation, held once, and then dropped.

  7. Let Forge close it

    A session is not over until next_session.first_action is written. If you are about to walk away, say "let's close" and give it a minute. Quitting the terminal mid-session costs you tomorrow's opening move, which is the single most valuable line in the ledger.

Reading the board

Six numbers, on the dashboard and in every forge-ledger show. This is what they mean before you have any of your own.

—sessions
—phase
—week
—at ceiling
—exit criteria
opengate

Sessions you have actually run · the phase you are in and its number · where you are on your track, if you chose one · concepts finished at their ceiling · exit criteria demonstrated out of the total · and whether the next phase is reachable or the capstone still blocks it.

None of these move because time passed. Sessions counts sittings, not days; concepts reach their ceiling on observed evidence; the gate opens on a capstone. A month away changes none of them, which is the point.

The panels

Pick up here

The literal next move — "open x.ts, add y." Across the top because it is what you need at minute zero and nothing else is.

Phase and gate

Sessions, concepts at ceiling, hours. Open means the next phase is reachable; LOCKED means a capstone hasn't passed yet.

The week

Six bars, Monday to Saturday, each against the 1.5-hour floor. It shows the shape of a week, which a single number cannot.

Exit criteria

What you have to demonstrate to finish the phase — tasks, never topics. They are the gate, not a checklist of subjects.

Wins

The centre panel and the biggest thing on the page: concrete things you can do now that you couldn't. It grows all year. Six per page.

Concepts

Level against ceiling, per concept. A ceiling-3 concept sitting at 3 is done, not neglected — that is what makes the plan finishable.

The timer holds the session's edges

Twenty-five-minute blocks, five-minute breaks, fifteen after every fourth. Beyond that it enforces three limits, and only the first two are yours to answer.

AtWhat happensWhose call
1.5 hoursAsks whether to keep going. This is the floor a session should clear, so it is also the first point where stopping is a real option.Yours
3 hoursAsks again.Yours
5 hoursCloses the day. No question, no override.Not yours
10pm–7amWill not start.Not yours

The last two are not productivity theatre. Most people doing this are fitting it around a job, which means a late session borrows from the few hours the plan actually has. And learning that never gets a night to consolidate does not survive the week — sleep is part of the method, not time off from it.

The ledger

One JSON file under git at ~/.claude/forge/ledger.json. Every session leaves a commit.

forge-ledger show                 # your state, readable
forge-ledger show --json          # the raw shape
git -C ~/.claude/forge log        # one commit per patch
git -C ~/.claude/forge show HEAD  # what last session changed

To undo a session that recorded something wrong, revert its commit — git -C ~/.claude/forge revert <sha>. To start the whole apprenticeship over, delete the directory. Both are real options and neither is an emergency.

Never edit ledger.json by hand

  • The hook will stop you, and it is stopping you for a reason: a hand-edit succeeds even when it is wrong, and nothing surfaces the breakage. A ledger that quietly starts lying is worse than one that is missing, because you find out in month seven.
  • If Forge itself tries a direct write and gets denied, that is the system working. It will retry through the CLI.

When a gate locks

A phase locks when its capstone doesn't pass. You haven't failed anything — you've found the part that needs more reps, which is what the step is for.

  • A training room opens the same session: ten exercises aimed at the one thing that broke, not at the whole phase.
  • One exercise per session, maximum. It is remediation, not a grind.
  • Three consecutive failures anywhere in the ramp means the missing piece is underneath this phase, not inside it. Forge stops, goes and finds the prerequisite, and teaches that instead. Let it.
  • You exit by passing all ten and then attempting a different capstone option — never the one you failed.

Coming back after a break

Absences are expected across a year. What ends programs is not the gap, it's the return.

  • Under two weeks — just resume. No review, and Forge will not mention it.
  • Two to eight weeks — one full session of retrieval before any new content. Expect one or two demotions; they are bookkeeping, not a verdict.
  • Over two months — you re-enter one phase below where you stopped, at its capstone. Pass it and you jump straight back.

Open exactly as you always do. Don't explain the absence. You will not be asked about it.

The moves that actually break this

  • Asking Forge to write the code. It will give you the next smallest hint instead, and that is the product you are paying for. The escape hatch exists — "just show me" — but you then modify what it showed you.
  • Skipping break-it and teach-back. Every tutorial on the internet omits those two. That is the reason tutorials don't work.
  • Saying you've got a concept instead of demonstrating it. Levels only move on observed evidence, and inflating one puts you in a build step you aren't ready for.
  • Working past the 5-hour stop or before 7am. Under pressure the instinct is to cut rest first. That trades the thing being built for the appearance of speed.

Sending your data back

Entirely optional, and nothing does it automatically. If you never run this command, nothing about your apprenticeship ever leaves your machine.

The record you build over a year is the best evidence there is for whether the curriculum works — where people get stuck, which explanations mislead, how long phases really take. That evidence is only useful in aggregate, and it is only worth having if it was given.

forge-ledger export "gpt-5"        # whichever model you used
forge-ledger export > report.json

In a chat window with no terminal, ask your model for it — the prompt carries the same field list and the same rules about what to leave out. It will only produce it if you ask; it is instructed never to suggest it.

What is left out, without you having to do anything

Your name, your goal in your own words, your constraint, your project, your metaphor domain, your wins, your open loops, your next action, and when you were last active. Which capstone you chose, what your training room was targeting, and the text of any Lab problem go too.

The constraint field is the one to notice: it routinely holds money, a visa, or a job situation. It is withheld first and it is never in the file.

What stays, and why

Where you stalled and which move unstuck you · what got demoted · the misconceptions you worked through · metaphors you outgrew · sessions and hours per phase · capstone outcomes · your concepts as level-against-ceiling. last_seen becomes "sessions ago" rather than a session number, so nothing in the file places you on a calendar.

Plus a backlog block: how many loops are open, how many exit criteria are unmet, how many rungs you still have to climb. Counts only — the text of your open loops is yours and stays out unless you add --open-loops, because it describes your project rather than the course.

Some of that is text you wrote — phase names, concept names, misconceptions. Read the file before you send it. The command prints exactly which fields those are, above the output.

How this is allowed to work

  • export prints to your screen. There is no endpoint, no key, no upload, and no version of this that sends anything on its own. Running it transmits nothing.
  • Sending the file is a separate thing you do on purpose, to a person, once you have read it.
  • If someone asks you for it and you would rather not, that is a complete answer and no one should ask twice.

If something's wrong

Grouped by what fails rather than by tool. The first one is the most common on anything that is not Claude Code, and it does not announce itself as an error.

The mentor isn't behaving like Forge

This is the failure that looks like success. You get a helpful, articulate assistant that explains things well — and none of the machinery. Tell-tale signs: it answers instead of asking, it hands you working code, it never mentions a phase or a gate, and it never asked for your ledger.

Test it directly. Ask: "which runtime are you in, and how do you know?" A model holding the prompt names agentic+hooks, agentic or chat and says how it checked. Anything vaguer and the prompt is not in context.

It keeps writing your code

Say so plainly: "don't write it — give me the next smallest hint." The spec is explicit that struggle is the mechanism, and a model that has the prompt will correct itself.

If it drifts back every session or two, that is instruction-following, not configuration. It is the clearest sign the model you have chosen is not strong enough to run this, and no amount of re-prompting fixes it.

For whoever maintains the curriculum

Everything above is for the person doing the apprenticeship. This last section is not — it is for whoever is changing the plan based on what comes back. If you are here to learn, you are done.

Comparing what comes back

§3.5 already says the record diagnoses the course rather than the learner. This just reads it across several people instead of one.

forge-ledger compare ana.json luis.json mira.json
forge-ledger compare *.json

It takes exports, not ledgers, so nothing personal is ever in the room. Every file is checked for "forge_export": 1 and refused otherwise.

The three things worth reading

rungs

The sum of ceiling − level across a learner's open concepts: the work actually left. It should fall between one person's exports. Rising rungs alongside rising sessions means concepts are arriving faster than they finish.

The rung warning

Fires when one §3.5 rung resolves over 40% of stalls. Rung 5 dominating means the plan outruns its foundations; rungs 1–3 mean the examples are too big. One learner is a bad week — three is a defect.

Shared misconceptions

The highest-value edit available. A wrong model two strangers both arrive at is a metaphor doing damage, and it is fixable in one pass.

Where it will mislead you

  • Rungs only count concepts already in play. It measures the current phase's backlog, not the whole programme's — someone in Phase 1 and someone in Phase 6 are not comparable on that column.
  • Misconception matching is word overlap. A hit is a strong signal; a miss is no information. Two learners working in different languages will never pair up automatically. Read the full lists.
  • Two or three exports tell you almost nothing. This starts earning its keep around five or six. Until then treat every pattern as a hypothesis, not a finding.

Manual de campo de Forge

Cómo llevar el aprendizaje · complemento del spec §1–§10

Forge es el mentor. Esto es la maquinaria a su alrededor: qué ejecutar, en qué orden, y qué partes no son negociables. No asume nada sobre qué modelo usas, ni sobre si has escrito una línea de código alguna vez.

Dos formas de entrar

Forge no depende de Claude, y no exige que ya sepas programar. Esas dos cosas te dan una elección, y para la mayoría de quienes llegan aquí la primera columna es la correcta.

sin instalar nada

Nunca has programado

Abre cualquier modelo de chat que ya tengas. Pega un archivo dentro. Di «empezar». Esa es toda la instalación: sin terminal, sin Node, sin nada que instalar.

→ Ruta A, más abajo

capacidad completa

Te manejas en una terminal

Clona el repositorio, ejecuta dos comandos, y el mentor podrá leer tus archivos, ejecutar tus tests y ver el error real. Esta es la configuración de referencia, y la única que puede evaluar la depuración.

→ Ruta B, más abajo

Qué puede hacer realmente cada ruta

El prompt averigua en cuál de los tres runtimes está antes de decir nada, y lo registra. Conviene leer esto antes de elegir, porque es lo que cuesta la elección.

RuntimeQué esQué pierdes
agentic+hooksClaude Code con el hook de protección instaladoNada. Es la referencia.
agenticCualquier agente con shell y acceso a archivos: otra CLI, un agente de IDE, un modelo local dentro de un agenteLa ruta de escritura protegida. Se sustituye por el guard de permisos en la Ruta B.
chatUna ventana de chat sin herramientasAcceso a archivos, la CLI, el historial de git, y cualquier lectura honesta del nivel 5.

Lo que estás cediendo, dicho claramente

  • En chat no se puede evaluar el nivel 5. «Depura» significa diagnosticar un fallo que el modelo vio ocurrir. Un modelo que no puede ejecutar nada te está creyendo a ti, y los niveles solo suben con evidencia observada. El prompt le indica que sea más lento en promover más allá del 4 y que explique por qué. Espéralo, y no lo discutas hasta convertirlo en un 5.
  • En chat no hay validación ni historial. Sin comprobación de esquema, sin escritura atómica, sin git. El ledger se regenera de cero cada sesión, y los documentos regenerados se van desgastando: las listas largas se acortan sin avisar. Comprueba que wins y misconceptions no hayan encogido.
  • Chat suspende dos reglas. «Nunca cargues tú con tu propio estado» y «nunca imprimas el ledger en el chat» dejan de aplicarse, porque ninguna es posible sin una CLI. Es el único punto donde el spec se anula.
  • Sin dashboard, la §7.1 se invierte. «No recites lo que ya pueden ver» solo vale mientras puedas verlo. Sin el tablero, el mentor tiene que decirte dónde estás, en voz alta, cada sesión.
  • El límite real es el contexto, no la marca. El prompt más el ledger rondan los 25k tokens antes de empezar la sesión, y crecen todo el año. Un modelo local pequeño lo aceptará todo y luego descartará en silencio el ciclo de la lección y los gates, que son el producto entero. Antes de confiarle un año, comprueba que siga negándose a avanzar una fase que no te has ganado.

Ruta A — empezar en una ventana de chat

Tres pasos. Ninguno requiere tener nada instalado.

  1. Consigue el prompt

    Abre FORGE-PROMPT.md del repositorio: el archivo entero, unos 95 KB de texto. No hace falta que lo entiendas. Hace falta que lo copies.

  2. Pégalo en tu modelo como system prompt

    Sirve cualquier sitio con una ventana de contexto larga. Si no hay casilla de «system prompt», pégalo como primer mensaje y envía un segundo mensaje diciendo empezar.

  3. Guarda lo que te devuelva

    Al final de cada sesión imprimirá un bloque de JSON. Guárdalo en un archivo llamado ledger.json, donde quieras; el escritorio vale. La sesión siguiente, pega ese archivo primero. Ese archivo es todo tu progreso; sin él, la sesión dos empieza de cero.

    Guarda al lado las dos versiones anteriores como ledger-1.json y ledger-2.json. En este modo no hay deshacer, y esos dos archivos son todo lo que tienes.

Qué estás cediendo, y cuándo dejar de cederlo

  • El mentor no puede ejecutar tu código, así que no puede verte depurar, y depurar es el peldaño más alto de la escalera. Tiene instrucciones de ser más lento en promoverte más allá del nivel 4 y de decirte por qué. Eso es comportamiento correcto, no el modelo poniéndose difícil.
  • No hay validación ni historial en tu ledger. Se regenera de cero cada sesión, y los documentos regenerados se desgastan: comprueba que tu lista de wins nunca se acorte.
  • Esto es temporal y está pensado para serlo. La Fase 0 te enseña la terminal, Node, npm y git, que es exactamente lo que necesita la instalación completa. Al terminar la Fase 0 podrás hacer tú mismo la instalación de abajo, y hacerlo cuenta como trabajo de la Fase 0, no como un trámite. El mentor tiene instrucciones de ofrecértelo entonces y no antes.

→ Tu instalación está lista. Sigue en Una sesión, de principio a fin.

Ruta B — parte uno: la maquinaria

Igual en todas las herramientas. Asume que ya sabes usar una terminal; si todavía no, coge la ruta de chat de arriba y vuelve al terminar la Fase 0.

  1. Instala y compila

    cd ~/projects/the-forge
npm install
npm run setup

    Esto compila la CLI del ledger, escribe FORGE-PROMPT.md en la raíz del repositorio —el prompt en sí, que toda herramienta necesita— y deja forge-ledger en ~/.local/bin. También escribe un skill de Claude Code, que puedes ignorar si no usas Claude Code.

  2. Comprueba que la CLI esté accesible

    which forge-ledger
# /home/tu-usuario/.local/bin/forge-ledger

    Si no imprime nada, ~/.local/bin no está en tu PATH. Añádelo al perfil de tu shell: sin eso, el mentor no puede leer ni escribir tu ledger en absoluto.

  3. Protege el ledger

    Un ledger editado a mano falla en silencio, así que algo tiene que hacer imposible la escritura directa. Cuál, depende de tu herramienta.

    Claude Code puede rechazar una escritura antes de que ocurra. Añade esto a ~/.claude/settings.json, combinado con lo que ya haya:

    "hooks": {
  "PreToolUse": [{
    "matcher": "Edit|Write|MultiEdit|NotebookEdit",
    "hooks": [{
      "type": "command",
      "command": "<repo>/scripts/guard-ledger.sh"
    }]
  }]
}

    Todo lo demás obtiene la misma protección del sistema de archivos:

    npm run protect-ledger    # chmod 444 ledger.json

    Una edición accidental falla entonces con EACCES, mientras forge-ledger escribe con normalidad, porque sustituye el archivo renombrando uno nuevo encima. Ejecútalo cuando ya tengas un ledger: antes de la sesión uno no hay nada que proteger.

  4. Verifica

    forge-ledger show

    Tu ledger, en el orden de la §7. Si dice que no existe ningún ledger, tu primera sesión será el onboarding.

En Claude Code — el skill entero, a mano

Un skill es un archivo Markdown dentro de una carpeta con nombre. Nada más:

mkdir -p ~/.claude/skills/forge
# luego escribe ~/.claude/skills/forge/SKILL.md como:
#   el frontmatter de abajo, una línea en blanco, y todo FORGE-PROMPT.md
---
name: forge
description: Run a session of the Forge apprenticeship. Reads the
  learner's ledger, opens as the spec directs, teaches, and writes
  back what was demonstrated. Invoke when the learner types /forge.
---

El nombre de la carpeta es el comando, así que skills/forge/ te da /forge. La description es lo que Claude lee para decidir que el skill aplica, y por eso nombra el disparador explícitamente.

npm run install-skill hace exactamente esto y nada más: concatena el frontmatter y el prompt en esa ruta. Hazlo a mano una vez si quieres comprobar que no hay magia. Reinicia Claude Code después, o el skill no aparecerá en la lista.

En cualquier otra cosa

  • Busca en la tabla de arriba el mecanismo de instrucciones permanentes de tu herramienta.
  • Dale todo FORGE-PROMPT.md. Son unos 95 KB: largo, pero los gates y el ciclo de la lección son el producto, y una versión resumida se deja ambos por el camino.
  • Si la herramienta carga un archivo por ruta, apunta al archivo para que siga sincronizado al recompilar. Si quiere texto, pégalo y vuelve a pegarlo tras cada cambio.

Comprueba que ha calado. Abre una sesión y pregunta: «¿en qué runtime estás, y cómo lo sabes?» Un modelo que ha cargado el prompt nombra agentic+hooks, agentic o chat y dice que lo comprobó ejecutando forge-ledger show. Cualquier respuesta más vaga significa que el prompt no llegó, y estás hablando con un asistente amable en lugar de con Forge.

Una sesión, de principio a fin

Los mismos siete movimientos cada vez, sean cuales sean tus horas.

  1. Abre el tablero primero

    cd ~/projects/the-forge && npm run dev
# http://localhost:5173

    Lee la tarjeta Pick up here antes que nada. Se escribió para este momento exacto, por alguien que sabía que llegarías sin recordar la vez anterior. Haz lo que dice.

  2. Abre tu agente en el proyecto que estás construyendo

    cd ~/ruta/a/tu-proyecto
# y abre aquí tu agente — claude, codex, gemini, cursor…

    No en the-forge. En un runtime agentic, Forge puede leer tus archivos y ejecutar tus tests, y ahí está la mayor parte de su valor: arráncalo donde está el trabajo.

  3. Empieza la sesión

    En Claude Code eso es /forge. En cualquier otra herramienta es lo que invoque las instrucciones permanentes que configuraste en la parte dos, que a menudo es simplemente abrir una conversación en el proyecto o la persona que contiene el prompt, y decir empezar.

    Ese es todo el prompt. No resumas la sesión anterior, no pegues tu ledger, no expliques dónde lo dejaste. Forge lee el ledger él mismo antes de decir una palabra, y sabe más de tus últimas diez sesiones que tú. (La única excepción es el runtime chat, que no puede leer archivos: ahí, pegar el ledger es el primer movimiento, y Forge te lo pedirá.)

  4. Arranca el temporizador cuando empieces de verdad

    No cuando te sientas, sino cuando empieza el primer bloque. Todo lo que el dashboard dice sobre tu semana depende de que esto sea honesto.

  5. Trabaja el ciclo

    Una sesión abre con una orientación de una línea y una comprobación de recuperación sobre algo que no has tocado en varias sesiones. Luego el bloque en sí. Espera que te pidan predecir la salida antes de ejecutar, romper algo que funciona, y explicarlo de vuelta sin la metáfora. Esos tres son donde aterriza el aprendizaje; también son los que parecen saltables.

    Si vienes plano, dilo. Hay un menú —push, consolidate, play, cold check, lab— y elegir consolidate tres sesiones seguidas es marcar el ritmo, no quedarse atrás.

  6. Di cuándo puedes volver

    Forge pregunta al cerrar: qué días, y más o menos a qué horas. Responde con la verdad y no con el plan que te gustaría cumplir: «martes y jueves por la mañana, sábado si la semana acompaña» es mejor respuesta que «casi todas las tardes» si casi todas las tardes es aspiracional.

    Lo usa para marcar el ritmo, no para presionar. Nadie está comprobando si apareciste, y el número nunca se convierte en una fecha límite (§1: la restricción no es el objetivo). Lo que hace es evitar que el plan se dimensione para una semana que no tienes: la forma más común en que fracasan estos programas es un calendario construido sobre horas que nunca fueron reales.

    Si tu disponibilidad cambia, dilo en cualquier apertura. Es una conversación de planificación, se tiene una vez, y luego se deja.

  7. Deja que Forge la cierre

    Una sesión no ha terminado hasta que next_session.first_action está escrito. Si estás a punto de marcharte, di «cerremos» y dale un minuto. Salir a mitad de sesión te cuesta el movimiento de apertura de mañana, que es la línea más valiosa del ledger.

Sesiones que realmente has hecho · la fase en la que estás y su número · dónde vas en tu track, si elegiste uno · conceptos terminados en su techo · criterios de salida demostrados sobre el total · y si la siguiente fase es alcanzable o el capstone todavía la bloquea.

Ninguno de estos se mueve porque pase el tiempo. Sesiones cuenta sentadas, no días; los conceptos llegan a su techo con evidencia observada; el gate se abre con un capstone. Un mes fuera no cambia ninguno, y ese es justamente el punto.

Los paneles

Pick up here

El siguiente movimiento literal: «abre x.ts, añade y». Arriba del todo porque es lo que necesitas en el minuto cero y nada más lo es.

Fase y gate

Sesiones, conceptos en su techo, horas. Open significa que la siguiente fase es alcanzable; LOCKED significa que un capstone aún no ha pasado.

La semana

Seis barras, de lunes a sábado, cada una contra el suelo de 1,5 horas. Muestra la forma de una semana, que un solo número no puede.

Criterios de salida

Lo que tienes que demostrar para terminar la fase: tareas, nunca temas. Son el gate, no una lista de asignaturas.

Wins

El panel central y lo más grande de la página: cosas concretas que ahora puedes hacer y antes no. Crece todo el año. Seis por página.

Conceptos

Nivel contra techo, por concepto. Un concepto de techo 3 que está en 3 está terminado, no descuidado: eso es lo que hace que el plan se pueda acabar.

Los límites del temporizador

Bloques de veinticinco minutos, descansos de cinco, quince después de cada cuarto. Más allá de eso impone tres límites, y solo los dos primeros los decides tú.

A lasQué pasaQuién decide
1,5 horasPregunta si quieres seguir. Es el suelo que una sesión debería alcanzar, así que también es el primer punto donde parar es una opción real.Tú
3 horasVuelve a preguntar.Tú
5 horasCierra el día. Sin preguntar, sin excepciones.No tú
22:00–07:00No arranca.No tú

Los dos últimos no son teatro de productividad. Casi todo el mundo que hace esto lo encaja alrededor de un trabajo, y eso significa que una sesión tardía roba de las pocas horas que el plan realmente tiene. Y un aprendizaje que nunca tiene una noche para consolidarse no sobrevive la semana: dormir es parte del método, no tiempo libre de él.

El ledger

Un archivo JSON bajo git en ~/.claude/forge/ledger.json. Cada sesión deja un commit.

forge-ledger show                 # tu estado, legible
forge-ledger show --json          # la forma cruda
git -C ~/.claude/forge log        # un commit por patch
git -C ~/.claude/forge show HEAD  # qué cambió la última sesión

Para deshacer una sesión que registró algo mal, revierte su commit: git -C ~/.claude/forge revert <sha>. Para empezar todo el aprendizaje de nuevo, borra el directorio. Las dos son opciones reales y ninguna es una emergencia.

Nunca edites ledger.json a mano

  • El hook te detendrá, y te detiene por una razón: una edición a mano tiene éxito aunque esté mal, y nada saca el problema a la superficie. Un ledger que empieza a mentir en silencio es peor que uno que falta, porque te enteras en el mes siete.
  • Si el propio Forge intenta una escritura directa y se la deniegan, eso es el sistema funcionando. Reintentará por la CLI.

Cuando una fase se bloquea

Una fase se bloquea cuando su capstone no pasa. No has suspendido nada: has encontrado la parte que necesita más repeticiones, que es para lo que existe el paso.

  • Se abre una training room en la misma sesión: diez ejercicios dirigidos a la única cosa que falló, no a la fase entera.
  • Un ejercicio por sesión, como máximo. Es remediación, no una paliza.
  • Tres fallos seguidos en cualquier punto de la rampa significan que la pieza que falta está debajo de esta fase, no dentro. Forge para, va a buscar el prerrequisito y enseña eso. Déjale.
  • Sales aprobando los diez y luego intentando una opción de capstone distinta, nunca la que fallaste.

Volver tras una pausa

Las ausencias son esperables a lo largo de un año. Lo que acaba con los programas no es el hueco, es la vuelta.

  • Menos de dos semanas — simplemente retoma. Sin repaso, y Forge no lo mencionará.
  • De dos a ocho semanas — una sesión entera de recuperación antes de cualquier contenido nuevo. Espera una o dos demotions; son contabilidad, no un veredicto.
  • Más de dos meses — vuelves a entrar una fase por debajo de donde lo dejaste, por su capstone. Si lo pasas, saltas directamente de vuelta.

Abre exactamente como siempre. No expliques la ausencia. No te van a preguntar por ella.

Los movimientos que sí rompen esto

  • Pedirle a Forge que escriba el código. En su lugar te dará la siguiente pista más pequeña, y eso es el producto que estás pagando. La salida de emergencia existe —«enséñamelo y ya»— pero luego modificas lo que te enseñó.
  • Saltarte «rómpelo» y «explícalo de vuelta». Todos los tutoriales de internet omiten esos dos. Por eso los tutoriales no funcionan.
  • Decir que dominas un concepto en vez de demostrarlo. Los niveles solo se mueven con evidencia observada, e inflar uno te mete en un paso de construcción para el que no estás listo.
  • Trabajar más allá del corte de 5 horas o antes de las 7:00. Bajo presión el instinto es recortar primero el descanso. Eso cambia lo que se está construyendo por la apariencia de velocidad.

Compartir tus datos

Totalmente opcional, y nada lo hace automáticamente. Si nunca ejecutas este comando, nada de tu aprendizaje sale jamás de tu máquina.

El registro que construyes durante un año es la mejor evidencia que existe sobre si el plan de estudios funciona: dónde se atasca la gente, qué explicaciones despistan, cuánto duran las fases de verdad. Esa evidencia solo sirve en conjunto, y solo merece la pena tenerla si fue dada.

forge-ledger export "gpt-5"        # el modelo que hayas usado
forge-ledger export > report.json

En una ventana de chat sin terminal, pídeselo a tu modelo: el prompt lleva la misma lista de campos y las mismas reglas sobre qué dejar fuera. Solo lo producirá si se lo pides; tiene instrucciones de no sugerirlo nunca.

Qué se queda fuera sin que tengas que hacer nada

Tu nombre, tu objetivo con tus propias palabras, tu restricción, tu proyecto, tu dominio de metáforas, tus wins, tus open loops, tu próxima acción y cuándo estuviste activo por última vez. También se van qué capstone elegiste, a qué apuntaba tu training room, y el texto de cualquier problema de Lab.

El campo constraint es el que conviene notar: suele contener dinero, un visado o una situación laboral. Se retiene el primero y nunca aparece en el archivo.

Qué se queda, y por qué

Dónde te atascaste y qué movimiento te desatascó · qué bajó de nivel · las misconceptions que trabajaste · metáforas que se te quedaron pequeñas · sesiones y horas por fase · resultados de capstones · tus conceptos como nivel-contra-techo. last_seen pasa a ser «hace n sesiones» en vez de un número de sesión, así que nada en el archivo te sitúa en un calendario.

Más un bloque backlog: cuántos loops están abiertos, cuántos criterios de salida faltan, cuántos peldaños te quedan por subir. Solo cuentas: el texto de tus open loops es tuyo y se queda fuera salvo que añadas --open-loops, porque describe tu proyecto y no el curso.

Parte de eso es texto que escribiste tú: nombres de fase, nombres de conceptos, misconceptions. Lee el archivo antes de enviarlo. El comando imprime exactamente cuáles son esos campos, encima de la salida.

Cómo se permite que funcione esto

  • export imprime en tu pantalla. No hay endpoint, ni clave, ni subida, ni ninguna versión de esto que envíe algo por su cuenta. Ejecutarlo no transmite nada.
  • Enviar el archivo es algo aparte que haces a propósito, a una persona, después de haberlo leído.
  • Si alguien te lo pide y prefieres no darlo, esa es una respuesta completa y nadie debería insistir.

Si algo va mal

Agrupado por lo que falla, no por herramienta. El primero es el más común en cualquier cosa que no sea Claude Code, y no se anuncia como un error.

El mentor no se comporta como Forge

Este es el fallo que parece un éxito. Tienes un asistente amable y elocuente que explica bien las cosas, y nada de la maquinaria. Señales delatoras: responde en vez de preguntar, te entrega código que funciona, nunca menciona una fase ni un gate, y nunca te pidió el ledger.

Compruébalo directamente. Pregunta: «¿en qué runtime estás, y cómo lo sabes?» Un modelo que tiene el prompt nombra agentic+hooks, agentic o chat y dice cómo lo comprobó. Cualquier cosa más vaga y el prompt no está en el contexto.

Comparar lo que llega

La §3.5 ya dice que el registro diagnostica el curso y no al aprendiz. Esto simplemente lo lee a través de varias personas en vez de una.

Toma exports, no ledgers, así que nada personal entra nunca en la sala. Cada archivo se comprueba buscando "forge_export": 1 y se rechaza si no lo tiene.

Las tres cosas que merece la pena leer

rungs

La suma de techo − nivel sobre los conceptos abiertos de un aprendiz: el trabajo que realmente queda. Debería bajar entre exports de una misma persona. Que suba mientras suben las sesiones significa que llegan conceptos más rápido de lo que se terminan.

El aviso de rung
